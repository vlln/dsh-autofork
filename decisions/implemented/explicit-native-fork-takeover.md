# 官方分叉关系与显式接管

分类：feature / architecture

## Problem

官方 fork 生成的普通会话已有持久化父指针，但插件目前只识别自己的分叉边。直接把官方边加入现有家族函数，会同时扩大取消权限、后台计数，并把普通分支误认为自动接管目标。

## Decision

- 关系展示合并官方普通分叉与插件分叉，官方关系以会话 header.parentSession 为依据，排除 subagent 委派关系。不按标题猜测，不修改原会话历史。
- 展示关系不自动建立接管。官方分支默认不自动回注、不作为新的后台任务计数，不改变用户指令路由。
- 只有直接子会话提供“接手原会话”，用户确认后建立单目标接管绑定。原会话不中止；后续指令交给接手会话，原会话的自动结果回传沿绑定投递。
- 自动回注开关仍属于发送方，选择接管不重置 muted。
- 接管选择持久化并拒绝循环；图关系、接管路由、显式通信授权、取消授权和后台计数分别判定。
- 普通官方分支显示无编号分叉标记，不给它分配 autofork 历史序号，不改用户标题。
- 接管不追补分叉后全部历史，只通过消息补充进度说明。

## Alternatives considered

- 把所有官方 fork 当成 autofork：用户没有同意自动接管，会产生意外路由和通知。
- 只增加树节点不拆授权：表面是展示变化，实质会放大取消权限和并发计数范围。
- 重新复制原会话全部历史：破坏用户选择的分叉点和已经存在的子会话内容。

## Consequences

保留现有自动分叉行为，为普通分支增加显式选择。确认 UI 与后端二次校验都必需；失败不得留下已生效的部分绑定。

验证：隔离 DSH 0.2.0-rc.2 的官方 Fork session 实际生成子会话；新父子关系与已有 autofork 同树显示，官方子节点默认无绑定并提供接管按钮。真实确认对话框取消后绑定不变；接受后 driver 指向该子会话，卡片显示“已接手原会话”；隔离进程重启后绑定恢复。未向模型发送新任务，未实测真实模型的后续指令转交/结果回传（该部分由回归测试覆盖）。

并发互斥目前限同进程的同父请求，存储后端无跨进程 CAS。旧版仅有历史边的数据不按后代时间猜测接管目标；新自动分叉与显式选择会写独立绑定。
